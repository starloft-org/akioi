# 题目导入包格式

在「后台 → 题库管理」建好题库，再到「后台 → 题目管理 → 导入题目」上传 zip 包，即可一次建好题目和测试数据。

## 一、先建题库

题号不再手工填写，而是由题目所属的**题库**统一分配。

1. 进入「后台 → 题库管理 → 新建题库」
2. 填题库名称
3. 填**题库前缀**，例如 `A`
4. 填**题号长度**，例如 `4`
5. 保存后这个题库的题号就是 `A` + 4 位序号：`A0000`、`A0001`、`A0002`……

规则说明：

- 题号 = 前缀 + 序号，序号左补零到「题号长度」位，题库内自动递增
- 前缀以字母开头，可带数字，最多 8 位；不同题库的前缀不能重复
- 前缀与题号长度之和不能超过 16 位
- 自建题库的**前缀和题号长度创建后不可修改**，只能改题库名称和备注，避免历史题号漂移
- 自建题库下还有题目时不能删除
- 站点初始化时会预置三个题库：**主库**（前缀 `A`，长度 4）、**团队库**（前缀 `T`，长度 6）、**个人库**（前缀 `P`，长度 6）
- 这三个预置题库不能删除，但可以在题库管理里修改前缀与题号长度；保存后会按题目原序号重新生成该题库下的所有题号
- 主库给后台创建的公共题目使用；团队库与个人库给「我的题目」里的团队题、个人题自动分配题号，后台导入题目请使用主库或其他自建题库，不要往这两个预置题库里导入

导入题目、新建题目都必须选择题库；不选时归入主库。换题库保存会把该题按新题库的规则重新编号。

## 二、包结构

```
题目包.zip
├── problem.md      必填，题面
├── config.json     可选，元信息
├── subtasks.json   可选，子任务与分值
├── 1.in
├── 1.out
├── sample.in
└── sample.out
```

- 题面必须叫 `problem.md`，不要改成 `题面.md` 之类
- 测试数据文件名不限：任意同名的一对 `.in` / `.out`（或 `.ans`）就是一组测试点，不要求是数字
- 顺序按文件名自然排序（`2` 在 `10` 前，`a` 在 `b` 前），导入后统一落盘为 `1.in`、`2.in`……
- 测试数据可以放在子目录里，导入时只看文件名
- 不放任何 `.in/.out` 也能导入，等同于“先建题、之后再传数据”
- **包内不需要写题号**，`config.json` 里的 `display_id` 会被忽略，题号由所选题库自动分配
- 一次可以上传多个 zip，但**严格串行**：前端一包一个请求，上一个包整包校验通过并入库后才发下一个，不做并发
- 上传完成接口立刻返回 `task_id`，解析、入库、推送测试数据都在后台任务里进行，前端轮询 `GET /api/admin/v1/import-tasks/:task_id` 显示进度（包序号、包内题目进度、当前阶段），上传大包也不会因为请求超时而卡住
- 后台任务只存在服务端进程内存里：后端重启后任务记录会失效，前端会明确提示「导入任务已不存在，请重新上传这个包」，不会一直停在 0%
- **整包原子**：包内任一题目不合格（缺 `problem.md`、测试点不成对、超出上限等）时整个 zip 都不导入，服务端不会留下半成品；弹窗按包累加「正在导入第 x 个 / 共 y 个包，成功 a 个」
- 任一个包失败就立即停下，不再发后面的包：弹窗显示「已停止：<包名>：<原因>」，修好该包后点「重试」从失败的这个包继续，已成功的包不会重复导入
- 可以点「选择题目包目录」一次把整个目录里的 zip 都选进来（浏览器会带上相对路径），导入记录里会记住这次导入的目录名和每个包的相对路径
- 导入中途失败或直接关掉弹窗，记录都留在浏览器里：下次打开导入弹窗会显示「上次的目录」和还没导入的包，重新选一次那个目录再点「继续导入」即可，已成功的包自动跳过；记录里的包还在内存里时，直接点「重试」就能从失败的那个包接着导
- 进度条只显示「当前这个包」的进度：上传占前 30%，服务端解析、入库、推测试数据占后 70%（按包内题目数推进），不会混成整批的总进度
- 弹窗里的「待导入」列表只列还没导完的包：导完一个就从列表和记录里消失，留下来的就是需要重新上传的包（会标「上次失败」并带上失败原因）
- 后端进程重启导致任务记录丢失时会明确报错并提示重新上传这个包，不会卡在 0%
- 如果本地已经是很多个题目 zip，可以再打成一个外层 zip 一次上传：服务端会按包内的 `*.zip` 自动展开成一个个题目包再排队导入，展开出来的包数量与进度会体现在导入进度里
- 打包上传的约束：外层 zip 内最多 5000 个题目包，嵌套不超过 2 层，解压后总体积不超过 8 GB，单个题目包受「测试点大小上限」（`max_testdata_mb`）限制；外层 zip 里如果含 `problem.md`，则按单个题目包处理，不再展开
- 打包上传同样走后台任务：接口立即返回 `task_id`，进度用 `GET /api/admin/v1/import-tasks/:task_id` 轮询，导入过程中关闭页面不会中断（进程重启会丢失任务记录）
- 打包上传同样是整包原子：外层 zip 会先全部展开并逐个校验，任一内层包不合格则整批都不入库，失败原因逐条列在结果里；修好后点「重试」重新提交这个外层包即可
- 拆包上传让每个请求体都很小，一千题也不会撞上 nginx 的请求体上限或网关超时
- 浏览器会把这一批的文件名与导入状态记在 localStorage 里：刷新、断网或关掉页面后重新打开「导入题目」，弹窗顶部会显示「上次导入还没有完成：共 N 个，已完成 M 个，还剩 K 个」并列出剩余文件名；重新选择这些 zip 后点「开始导入」只会补导没成功的包，已成功的包不会重复导入（浏览器不保留文件本身，所以需要重新选一次），全部导入成功或点「丢弃记录」后记录才会清掉

## 三、problem.md

直接把洛谷题目页右上角**「复制 Markdown」**的内容贴进来即可，识别这些段落：

| 段落 | 来源 |
| --- | --- |
| 标题 | 一级标题 `# P1001 A+B Problem`，开头形如题号的文字会被去掉 |
| 题目描述 | `## 题目描述` |
| 输入格式 | `## 输入格式` |
| 输出格式 | `## 输出格式` |
| 样例 | `## 样例 #N` 下的 `### 样例输入 #N`、`### 样例输出 #N` 代码块 |
| 提示 | `## 提示` 或 `## 说明` |

兼容老版洛谷把输入输出合在一节的结构：`## 输入输出格式` 下用 `### 输入格式` / `### 输出格式` 分隔。

没有一级标题时，必须在 `config.json` 里写 `title`，否则导入会报“未能确定题目标题”。

## 四、config.json

可选，字段与后台新建题目一一对应：

```json
{
  "title": "A + B Problem",
  "difficulty": "入门",
  "time_limit_ms": 1000,
  "memory_limit_mb": 256,
  "points": 10,
  "tags": ["模拟", "入门"],
  "source": "洛谷 P1001",
  "visibility": 1
}
```

| 字段 | 说明 | 缺省 |
| --- | --- | --- |
| `title` | 标题，优先于题面的一级标题 | 取题面标题 |
| `difficulty` | 七级难度之一 | 留空 |
| `time_limit_ms` | 100–30000 | 1000 |
| `memory_limit_mb` | 16–2048 | 256 |
| `points` | 排行榜积分 | 按难度默认值 |
| `tags` | 标签数组 | 空 |
| `source` | 来源 | 空 |
| `visibility` | 1 公开，2 隐藏 | 1 |

难度取值：`入门`、`普及-`、`普及/提高-`、`普及+/提高`、`提高+/省选-`、`省选/NOI-`、`NOI/NOI+/CTSC`。

不在表里的字段一律忽略，写错字段名不会报错，但也不会生效。

## 五、测试数据

- 任意文件名的一对 `.in` / `.out`（或 `.ans`）就是一组测试点，不要求数字：`sample.in` + `sample.out`、`1.in` + `1.out` 都行
- 顺序按文件名自然排序（`2` 在 `10` 前面，`a` 在 `b` 前面），导入后统一落盘为 `1.in`、`1.out`、`2.in`……
- 去掉扩展名后必须成对，缺一个会报「测试点 sample 缺少输出文件（sample.out 或 sample.ans）」
- 允许跳号与任意前缀，名字大小写不敏感，大小写不同但同名的文件视为同一组
- 分值默认把 100 分均分到各测试点；要细调就在包里放 `subtasks.json`，按名字指定分值、把测试点编成子任务
- 子任务只有「组内全部测试点通过」才得该组的分，组内单个测试点自身不计分
- `subtasks.json` 的完整格式、计分规则和例子见 `docs/testdata.md`

## 六、限制与常见错误

| 项 | 限制 |
| --- | --- |
| zip 大小 | ≤ `MAX_TESTDATA_MB`，默认 512MB |
| 测试点数量 | ≤ `MAX_TESTCASES`，默认 100 |
| 题号 | 包内不指定，由导入时选中的题库按「前缀 + 定长序号」自动分配 |
| 导入任务 | 任务记录在内存里，保留 1 小时、最多 50 个；服务重启后进度与结果列表清空，已入库的题目不受影响 |

常见错误：

| 报错 | 原因 |
| --- | --- |
| 题目包必须是 zip 文件 | 上传了 `.rar`、`.7z` 或改后缀的压缩包 |
| 未能确定题目标题 | 题面没有一级标题，`config.json` 也没写 `title` |
| 测试点 sample 缺少输出文件（sample.out 或 sample.ans） | 只有 `.in` 没有同名的 `.out`/`.ans` |
| 尚未创建题库，请先在题库管理中新建题库 | 题库表为空，先去「题库管理」建一个题库 |
| 题库前缀已存在 | 新建题库时前缀与已有题库重复 |

导入以「整包」为单位在同一个数据库事务里完成：题号分配、题目记录、测试点记录一起提交，测试点文件先写到临时目录、通过校验后才落盘并入库，任一步失败都会回滚事务并删除已写入的目录，所以不会出现「题目建了但没有测试数据」或半包导入的情况。事务提交后才把测试数据推送到已配置的评测节点，推送失败的节点记录在题目详情的同步状态里，不影响题目本身已入库。

## 七、接口说明

接口一律异步：`POST /api/admin/v1/problems/import` 上传完立刻返回 `task_id`（只带一个 `files` 时也一样），解析、入库、推送测试数据都在后台任务里进行。

脚本或第三方调用可以一次提交多个包，同样拿到一个 `task_id`，再用下面的接口轮询进度。

```
GET /api/admin/v1/import-tasks/:task_id
```

个人题目走同一套机制，接口在 `/api/v1/my` 下：

```
POST /api/v1/my/problems/import      # 上传包，立即返回 task_id
GET  /api/v1/my/import-tasks/:task_id  # 轮询进度与结果
```

个人导入的题目会自动归入「个人库」（题号 P 开头），别人看不到；导入任务带上了创建者，别的用户查不到你的任务。

## 八、前端导入弹窗的行为

- 后台「题目管理」和「我的题目」都可以按目录或按 zip 批量导入。选目录时会记下目录名和每个包的相对路径，浏览器刷新后重新选同一个目录就能接着导。
- 待导入列表只显示还没导完的包：一个包整包成功入库后立刻从列表里消失，失败或没轮到的包留在列表里并标上「上次失败」和失败原因。
- 成功导入的包不再写进浏览器记录，所以记录里只剩需要重新上传的包；全部导完后记录自动清空。
- 进度条只反映当前这个包：上传占 0-30%，服务端解析、写库、推送测试数据占 30-100%。
- 任何一个包失败就停止，不再继续后面的包；点「重试剩余 N 个包」会从失败的那个包继续。

## 题目列表顺序

题目列表（公共题目、我的题目、团队题目、后台题目管理）统一按「题库 → 题号」排序：

1. 先按所属题库，顺序与「题库管理」里的题库顺序一致，新建得越早越靠前
2. 同一题库内按题号升序，例如 A0001、A0002、A0003
3. 排序不使用数据库 id，导入顺序、删除后重编号都不会让列表顺序跳动
