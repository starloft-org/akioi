# 评测进度与等待体验

评测是异步的：提交落库后状态是 `Pending`（排队中），评测节点取到任务后开始执行，结束时回传结果。这段时间里页面需要知道「还在排队 / 已经开始评测 / 测到第几个点」，否则用户只能盯着不动的页面。

## 一、状态流转

| 状态 | 含义 | 由谁写入 |
| --- | --- | --- |
| `Pending` | 已入库、在队列里等评测节点取任务 | 主站在创建提交 / 重测时写入 |
| `Judging` | 评测节点已经开始评测 | 评测节点上报进度时，主站把 `Pending` 改成 `Judging` |
| 其它（`Accepted`、`WrongAnswer`…） | 评测结束的最终状态 | 评测节点回传结果时写入 |

`Judging` 只在节点真正开始跑评测时出现；如果节点忙，页面会一直显示排队中的时长与前面排队的提交数。

## 二、进度是怎么传的

1. 评测节点开始评测时，先向主站 `POST /api/v1/internal/judge-progress` 报一次 `{submission_id, judge_token, status: "Judging", total: n}`（`done` 为 0）
2. 之后每跑完一个测试点，再报一次，`done` 递增
3. 主站把进度写进 Redis 的 `judge:progress:<提交 ID>`（JSON：`done` / `total` / `updated_at`，保留 30 分钟），并把提交状态推进到 `Judging`
4. 评测结果回传时，主站删除该进度键

上报失败只记日志，不影响评测本身；令牌对不上（提交已被重测覆盖）的进度会被丢弃。

## 三、页面轮询

- 详情页用轻量接口 `GET /api/v1/submissions/:id/status` 轮询，返回 `status`、`score`、`time_ms`、`memory_kb`、`judged_at`、`progress`、`pending_ahead`，不带源码与测试点明细
- 刚提交的 30 秒内每 700ms 轮询一次，之后降到 1500ms，直到状态不再是 `Pending` / `Judging`
- 状态变成最终结果后，页面再拉一次完整详情（源码、测试点结果）并停止轮询
- 排队中显示「排队中：前面还有 N 份提交」；评测中显示「评测中：已测 x / n 个测试点」和已等待秒数，进度条按测试点比例推进

## 四、列表页

评测记录列表只要有 `Pending` / `Judging` 的提交就每 1.5 秒刷新一次，全部结束自动停止，不用手动刷新。
